# 我为什么要自己做一个 Agent OS：从删掉 Session 开始

> 中文 | [English](#why-i-built-my-own-agent-os-starting-by-removing-sessions)

作为一个 AI 从业者，我接触过不少 Agent harness，比如 Claude Code、dsh 等等。它们都很强，也各自解决了一部分问题。

但用得越多，我越确认一件事：**我想要的 Agent，和它们默认的抽象不太一样。**

我想要的不只是一个更聪明的聊天框，也不是一个更长的上下文窗口。我想要一个有持续身份、能长期共处、可以不断扩展，但同时有明确边界的 Agent。

所以我开始自己做 NodeAgentOS。

## Session 是一个自然的设计，但我不想要它

Session 是现在大多数 Agent 产品的核心抽象：打开一个会话，带上这次需要的上下文，聊完，结束；下次再开一个新的。

这个设计很自然，但对我来说不够优雅。

因为每次打开一个新 Session，我都需要重新想：这次要告诉它什么？哪些背景要补？哪些偏好它已经知道了？而这些东西，我往往已经在不同的 Session 里重复说过很多次。

**Session 把“连续的关系”切成了很多段“任务”。**

所以在我自己的 harness 里，第一件事就是把 Session 从核心抽象里拿掉。

取而代之的，是一种全局的、持续的上下文管理方式：信息不需要被人为地搬来搬去，而是在长期互动中自然沉淀下来。

我的 Agent 更像是一个有自己身份的存在。我们在共处中磨合彼此，逐渐建立一种持续的互动关系，而不是每次见面都从零开始。

## 它应该是云端的，也应该能接上我的所有设备

我是一个有很多设备的人：笔记本、台式机、手机，还有公司的台式机。我经常在不同设备之间切换。

所以我不希望我的 Agent 只活在某台电脑的某个浏览器标签页里。

它应该在云端常驻。关掉网页，它还在；换一台设备，它还是同一个它；有任务没做完，它还能接着做。

这听起来像是“多端同步”，但本质上不是。多端同步同步的是数据；我想要的，是**同一个 Agent 的连续存在**。

## 它应该像操作系统一样扩展

我还希望它可以无限扩展。

不是每加一个能力，就往主程序里塞一个函数；而是像操作系统安装软件一样，可以不断接入新的应用，支持新的场景。

这就是 Node 的由来。

Node 是一个独立的能力单元，可以是电脑上的一个进程，也可以是服务器上的一项服务，甚至可以是另一台设备。它通过总线接入 Agent，声明自己能做什么，Agent 在运行时发现它。

Node 之间不需要互相 import，也不共享内存。一个 Node 崩了、重启了、搬到另一台机器，Agent 仍然可以活着。

**扩展 Agent 的方式，不是改核心，而是让一个新的 Node 从网络上加入。**

## 但它不能拥有无限权限

扩展能力的同时，我也很在意另一件事：权限。

我不希望 Agent 拥有无限权限。我只希望它在我允许的范围内行事。

这也是为什么 NodeAgentOS 在设计上把“核心”和“应用”分开：

- 核心是稳定的：Agent Loop、通信机制、权限管理、统一的 UI 框架
- 应用是自由的：开发者可以在上面构建各种 Node，定义自己的 UI 和逻辑

核心封闭、稳定，提供最基础的服务；应用开放、灵活，负责具体能力。

## UI/API 分离：把人的界面和 Agent 的权限分开

在扩展 Agent 能力的过程中，最大的冲突往往发生在应用端和 Agent 的权限之间。

一直以来，扩展 Agent 主要有两种方式。

第一种是代码/CLI。它能让 Agent 的能力极大地扩展，但自由度太大。Agent 做了什么、为什么这么做，用户很难感知，也很难有效控制。

第二种是 GUI Agent。它让模型直接操作屏幕，看起来什么都能做。但屏幕本来就是设计给人的，天然带着人的全权限。这里面有一个更大的问题：很多应用原本的防御边界会被突破。比如聊天软件本来是禁止群发的，如果 Agent 能操作屏幕，这条边界就不存在了。

所以我认为，**把 Agent 的操作权限和人的操作界面分开，是很有必要的。**

这就是 NodeAgentOS 的 UI/API 分离机制：

- UI 操作界面仍然留给人
- Agent 的逻辑和权限通过 API 进行管理和控制
- 平台负责让用户看清并控制 Agent 能做什么、不能做什么

人有人界面，Agent 有 Agent 的接口。两者不是同一套权限。

## 最后

把这些放在一起，就是我想要的东西：

一个没有 Session 切割、有持续身份的 Agent；  
一个云端常驻、能接上多台设备的 Agent；  
一个像操作系统一样可扩展，但有明确权限边界的 Agent。

这就是我开始做 NodeAgentOS 的原因。

# Why I Built My Own Agent OS: Starting by Removing Sessions

> [中文](#我为什么要自己做一个-agent-os从删掉-session-开始) | English

As someone working in AI, I've used many agent harnesses—Claude Code, dsh, and others. They are powerful, and each solves part of the problem.

But the more I use them, the more I'm convinced of one thing: **the Agent I want is built on different abstractions.**

I don't just want a smarter chat box, or a longer context window. I want an Agent with a persistent identity—one I can live with over time, extend continuously, and still keep within clear boundaries.

That's why I started building NodeAgentOS.

## Session Is a Natural Design. I Don't Want It.

Session is the core abstraction of most agent products today: open a conversation, bring the context it needs, finish, close it, and start a new one next time.

It's a natural design, but for me it isn't elegant enough.

Every time I open a new Session, I have to think again: what do I need to tell it this time? What background should I add? Which preferences does it already know? And I've usually repeated all of this across different Sessions many times.

**Session cuts a continuous relationship into a series of tasks.**

So in my own harness, the first thing I removed was Session as a core abstraction.

In its place is a global, continuous approach to context management: information doesn't need to be moved around by hand; it settles naturally through long-term interaction.

My Agent is more like a being with its own identity. We adapt to each other through coexistence and gradually build a continuous relationship, instead of meeting for the first time on every occasion.

## It Should Live in the Cloud and Connect to All My Devices

I'm someone with many devices: a laptop, a desktop, a phone, and a work desktop. I switch between them constantly.

So I don't want my Agent to live only in a browser tab on one computer.

It should live in the cloud. Close the page and it's still there; switch devices and it's still the same one; leave a task unfinished and it can pick it up again.

That sounds like "multi-device sync," but it isn't. Sync moves data. What I want is **the continuous existence of the same Agent.**

## It Should Extend Like an Operating System

I also want it to be endlessly extensible.

Not by stuffing another function into the main program every time I add a capability, but by installing new applications the way an operating system does—continuously adding new capabilities and scenarios.

That's where Node comes from.

A Node is an independent unit of capability. It can be a process on a computer, a service on a server, or even another device. It joins the Agent over a bus, declares what it can do, and the Agent discovers it at runtime.

Nodes don't need to import each other or share memory. If one Node crashes, restarts, or moves to another machine, the Agent can keep living.

**The way to extend an Agent isn't to change the core; it's to let a new Node join from the network.**

## But It Must Not Have Unlimited Permissions

As I extend its capabilities, I care about something else just as much: permissions.

I don't want an Agent with unlimited permissions. I want it to act only within the boundaries I allow.

That's why NodeAgentOS separates the "core" from "applications" by design:

- The core is stable: the Agent Loop, communication mechanisms, permission management, and a unified UI framework.
- Applications are free: developers can build Nodes on top, defining their own UI and logic.

The core is closed and stable, providing the most basic services. Applications are open and flexible, responsible for specific capabilities.

## UI/API Separation: Separate the Human Interface from Agent Permissions

When extending an Agent's capabilities, the biggest conflict often arises between the application side and the Agent's permissions.

There have traditionally been two ways to extend an Agent.

The first is code/CLI. It can dramatically expand what an Agent can do, but it offers too much freedom. It's hard for users to perceive what the Agent did and why, and hard to control effectively.

The second is a GUI Agent. It lets the model operate the screen directly, and it looks like it can do anything. But the screen was designed for humans, and it naturally carries a human's full permissions. There's a bigger problem here: many applications' defensive boundaries get broken. For example, a chat app may prohibit mass messaging. If an Agent can operate the screen, that boundary no longer exists.

So I believe it's necessary to **separate the Agent's operating permissions from the human's operating interface.**

That's the UI/API separation in NodeAgentOS:

- The UI remains with the human.
- The Agent's logic and permissions are managed and controlled through APIs.
- The platform makes it clear to users what the Agent can and cannot do.

Humans have a human interface; the Agent has an Agent interface. They are not the same set of permissions.

## In the End

Put it all together, and this is what I want:

An Agent with a continuous identity, not cut apart by Sessions.  
An Agent that lives in the cloud and connects to multiple devices.  
An Agent that extends like an operating system but has clear permission boundaries.

That's why I started building NodeAgentOS.

To put it a little romantically: I'm not trying to build a chat product. I'm trying to build a "silicon-based life" that can coexist with you over time.

It's still very early, but I'm clear about the direction.
